# Keep stale files for 7 days, dated by a stale record in the storage zone

`deploy` deletes a stale file only once it has been stale for 7 days, so a service worker or an open page running the previous build can still load that build's assets. The date a file went stale is stored in `.orbitpush/stale.json` in the storage zone, because the upload date bunny.net lists is when the file was uploaded, not when it left the build: an asset uploaded months ago would be deleted on the deploy that drops it. Keeping the record in the storage zone keeps the machine that runs `deploy` stateless, and costs a public file that lists only paths the site served before. Versioned deploys with routing by deployment ID, as Vercel does, would also fix this but need the app to send the ID; never deleting would make the deleted count meaningless and grow the zone without bound. The 7 days are not configurable, since a service worker that is offline longer serves the old build from its own cache. Revisit if a site needs rollback, which would need per-deploy manifests instead of one record, or if 7 days turns out too short or too long in use.
