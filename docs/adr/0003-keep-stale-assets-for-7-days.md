# Keep stale assets for 7 days, dated by a stale record in the storage zone

`deploy` deletes a stale asset (a `.js`, `.mjs`, `.css`, `.wasm`, `.json`, font or source map file) only once it has been stale for 7 days, so a service worker or an open page running the previous build can still load that build's lazy chunks, styles, route data and fonts. Every other stale file, HTML included, is deleted on the deploy that drops it: no open page needs the previous build's pages, and a removed page, PDF or image should stop being served, also when it was published by mistake. The list is fixed in code rather than set in `orbitpush.json`, because it follows what browsers and bundlers load after a page is open, not the site, and a wrong list breaks the app silently; a missing image is cosmetic until reload. A configurable number of days and a `--delete-stale` flag were considered and left out until a site needs them. Without an `index.html` in the output, `deploy` deletes stale files only after 7 days, so deploying the wrong or an empty directory does not delete the site.

The date a file went stale is stored in `.orbitpush/stale.json` in the storage zone, because the upload date bunny.net lists is when the file was uploaded, not when it left the build: an asset uploaded months ago would be deleted on the deploy that drops it. Keeping the record in the storage zone keeps the machine that runs `deploy` stateless, and costs a public file that lists only paths the site served before. Versioned deploys with routing by deployment ID, as Vercel's skew protection does, would also fix this but need the app to send the ID; never deleting would make the deleted count meaningless and grow the zone without bound. 7 days, because a service worker that is offline longer serves the old build from its own cache. Revisit if a site needs rollback, which would need per-deploy manifests instead of one record, or if a site needs another file type kept.
